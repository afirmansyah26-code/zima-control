# Application Registry Architecture Decisions

## Status

**Accepted implementation-aligned architecture decisions for the current Application Registry schema.**

This document records the Prisma-relevant decisions implemented in `prisma/schema.prisma` and identifies policies that remain deferred. It does not create a migration or select a secret storage backend.

`Accepted` identifies decisions encoded in the current schema or established by the source documents. Application-layer rules are described separately from database constraints. Policies that are not required for the v1 registry are marked `Deferred`.

The current working tree already contains changes to `prisma/schema.prisma` and `docs/MILESTONE-1A2-APPLICATION-REGISTRY-SCHEMA.md`. Those changes are not modified by this task.

| --- | --- | --- |

| Runtime container identity | Accepted | `containerId` is `@unique` for the current single-runtime-host assumption. |
| RuntimeContainer lifecycle | Accepted | Store current runtime containers only; reconcile/replace after successful runtime discovery. |
| Referential actions | Accepted / Deferred | Child snapshot relations use `onDelete: Cascade` and foreign-key relations use `onUpdate: Restrict`; root application deletion remains unresolved and has no explicit `onDelete`. |

## ADR-001 Internal ID Strategy

### Context

The registry needs an internal primary key for every model. The ERD defines `id PK` but does not select UUID, CUID, integer, or another physical format. The documents also state that the internal identity is distinct from the ZimaOS application ID.

The finalized schema uses `String @id @default(uuid())` for every registry model.

### Options

1. `String` generated by the application layer.
2. `String @default(uuid())` generated by Prisma.
3. `String @default(cuid())` generated by Prisma.
4. An integer generated by the database or Prisma.

### Decision

**Accepted:** use opaque `String` primary keys generated by Prisma with `@default(uuid())`. Keep internal IDs separate from `Application.zimaosAppId`, runtime `containerId`, application names, and Compose service names.

### Consequences

- Every model receives a UUID-backed string ID when a record is created.
- IDs are portable across SQLite and a later database provider.
- The application layer must not use external names or runtime IDs as internal primary keys.
- This decision avoids silently coupling internal identity to a mutable display name or an external ZimaOS identifier.

## ADR-002 ZimaOS External Identity

### Context

The ERD explicitly separates `zimaos_app_id` from the internal `Application.name`. The discovery flow should find an existing application by stable external identity when that identity is available. Some resources may not have a ZimaOS ID.

The finalized schema has:

```prisma
zimaosAppId String? @unique
```

A separate non-unique lookup index was not retained because the unique constraint supplies the lookup structure.

### Options

1. Nullable, indexed, and non-unique.
2. Nullable and unique, with multiple records allowed to have `NULL`.
3. Required and unique.
4. Use `Application.name` as the external identity.

### Decision

**Accepted:** `zimaosAppId` is nullable and unique when non-null. The unique constraint supplies lookup support, and the field remains separate from `Application.name`.

`Application.name` remains the canonical internal name and is already explicitly unique in the ERD. It may be stable when an application has no ZimaOS ID. `zimaosAppId` is the external discovery identity only when supplied by ZimaOS.

### Consequences

- Discovery can upsert by ZimaOS ID without using a display name as identity.
- Applications without a ZimaOS ID remain valid.
- Multiple resources without a ZimaOS ID remain representable through nullable values; provider behavior for multiple `NULL` values should still be verified during migration planning.
- An external ID change requires an explicit reconciliation policy; it must not silently create a duplicate application.

## ADR-003 Service Identity

### Context

A Compose service name is scoped to its deployment. Two deployments can both contain a service named `web`; global uniqueness would therefore be incorrect. The normalizer needs a stable key to upsert a service within the current deployment.

The finalized schema has a composite unique constraint:

```prisma
@@unique([deploymentId, name])
```

### Options

1. Global unique `name`.
2. Non-unique index on `(deploymentId, name)`.
3. Composite unique constraint on `(deploymentId, name)`.
4. Use an external container name as the service identity.

### Decision

**Accepted:** enforce `@@unique([deploymentId, name])`.

`ApplicationService.name` is the Compose service key and is unique only within its `ApplicationDeployment`. The internal `ApplicationService.id` remains the row primary key.

### Consequences

- Repeated normalization of the same deployment service is idempotent.
- The same service name can exist in different deployments.
- The persistence layer can use `(deploymentId, name)` for `upsert`.
- Renaming a service creates an identity-change decision for the normalizer; it must not be treated as a runtime container rename automatically.

## ADR-004 Environment Variable Identity

### Context

Environment values are not persisted as plaintext. The registry stores metadata for each environment key. A service can have many keys, but one normalized service snapshot should not contain duplicate rows for the same key.

The finalized schema has a composite unique constraint:

```prisma
@@unique([serviceId, key])
```

### Options

1. Global unique `key`.
2. Non-unique index on `(serviceId, key)`.
3. Composite unique constraint on `(serviceId, key)`.
4. Store environment metadata as one serialized object.

### Decision

**Accepted:** enforce `@@unique([serviceId, key])`.

`key` is unique within one service, not globally. The value is intentionally absent from the model. `type`, `isSecret`, `configured`, `present`, and `source` describe the metadata associated with the key.

### Consequences

- Normalization can safely upsert metadata by service and key.
- The same key can be used by different services.
- A Compose source that exposes duplicate declarations must be normalized before persistence; the schema will not represent competing values.
- Secret detection and redaction remain adapter responsibilities.

## ADR-005 Runtime Container Identity

### Context

`RuntimeContainer.containerId` identifies an actual runtime container. A container can be recreated, in which case a new runtime ID is expected. The runtime ID is not an application identity and must not replace `Application.id` or `zimaosAppId`.

The finalized schema has a unique constraint:

```prisma
containerId String @unique
```

### Options

1. Globally unique `containerId`.
2. Unique `(serviceId, containerId)`.
3. Non-unique index only.
4. Use `containerName` as the identity.

### Decision

**Accepted:** treat `containerId` as unique for a retained current runtime container. The row is replaced when the physical container is recreated and receives a new ID.

- This accepted decision assumes a single Docker/runtime namespace for this registry. If multiple runtime hosts are introduced, a host/runtime scope must be added before applying global uniqueness.

### Consequences

- A single physical container cannot be attached to two services accidentally.
- A recreated container receives a new row identity while the `Application` and `ApplicationService` identities remain unchanged.
- Historical observations do not reuse the same `containerId` under this current-only policy; history is deferred by ADR-011.

## ADR-006 RuntimeContainer Lifecycle

### Context

The source documents describe runtime information as the latest known state for a service and require runtime changes not to alter application identity. The relationship permits `0..N` runtime containers because a Compose service may have zero, one, or multiple current containers.

The two lifecycle choices are:

- one record represents a current runtime container, or
- the table stores historical observations.

### Decision

**Accepted:** `RuntimeContainer` stores current runtime containers only. One row represents one currently known physical container. A service may therefore have multiple current rows when it has multiple replicas, but it has no historical rows in the v1 registry.

After a successful and complete runtime discovery, the application layer reconciles the current set:

- insert newly observed containers
- update existing containers by `containerId`
- replace/remove rows for containers that were recreated or are no longer part of the authoritative current result

A failed or partial discovery must not delete current runtime rows.

### Consequences

- The schema remains normalized without adding a runtime history table.
- `observedAt` describes the freshness of the current row, not an immutable event record.
- Container recreation changes the runtime identity but not the application or service identity.
- A complete discovery boundary is required before stale-row removal is safe.
- Historical runtime debugging is not available in v1 and is covered by ADR-011.

## ADR-007 Referential Actions

### Context

The registry is a normalized aggregate:

```text
Application
  -> ApplicationDeployment
      -> ApplicationService
          -> ports, volumes, networks, environment metadata, runtime containers
```

Child records have required foreign keys and have no independent meaning outside their parent snapshot. At the same time, deleting an application should not casually erase deployment and runtime metadata.

### Options

- `Cascade` at every level.
- `Restrict` at every level.
- `SetNull` on child foreign keys.
- A mixed policy based on ownership and lifecycle boundaries.

### Decision

**Accepted for child snapshots, Deferred at the root:**

- `ApplicationDeployment -> ApplicationService`: `onDelete: Cascade`.
- `ApplicationService -> DeploymentPort`: `onDelete: Cascade`.
- `ApplicationService -> DeploymentVolume`: `onDelete: Cascade`.
- `ApplicationService -> DeploymentNetwork`: `onDelete: Cascade`.
- `ApplicationService -> EnvironmentVariable`: `onDelete: Cascade`.
- `ApplicationService -> RuntimeContainer`: `onDelete: Cascade`.
- All foreign-key relations use `onUpdate: Restrict`.

`Application -> ApplicationDeployment` has no explicit `onDelete` in the schema. Root application deletion remains unresolved and is not silently treated as `Restrict` or `Cascade`. Parent IDs are treated as immutable; no update cascade is used.

### Consequences

- An explicitly authorized deployment deletion removes dependent service snapshot records and their owned children instead of leaving orphans.
- Root application deletion still requires a separate lifecycle policy.
- `SetNull` is rejected because all child foreign keys are required and a detached port, volume, network, environment record, or runtime observation has no valid parent context.
- Full root cascade is rejected because it would make an application-level delete destructive by default.
- If retention or audit requirements later require preserving deleted deployment metadata, deletion policy must be revisited before migration.

## ADR-008 Port Representation

### Context

The ERD and examples use mappings such as `6091:6091/tcp`. The current model uses:

```prisma
published String
target    Int
protocol  String
```

Compose can express ranges and other long-form port details, but the current Application Registry scope does not establish a complete range model.

### Options

1. Support only a single target port in v1.
2. Store target ranges as strings.
3. Add separate start/end fields.
4. Add a raw structured port payload.

### Decision

**Accepted:** v1 supports a single target port with `DeploymentPort.target Int`. Keep `published` as `String` so the published side can preserve the documented string representation. Defer target port ranges and other advanced Compose port forms.

The normalizer must reject, flag, or explicitly defer an unsupported range. It must not silently truncate a range to one integer.

### Consequences

- The current schema remains aligned with the v1 examples.
- Basic mappings such as `6091:6091/tcp` are represented directly.
- Compose applications using target ranges require a later schema decision or an explicit unsupported-state policy.
- No range fields or serialized raw port field are added now.

## ADR-009 Timestamp Policy

### Context

Different timestamps answer different questions. Creation, internal modification, successful discovery, deployment capture, and runtime observation must not be treated as interchangeable.

The current schema contains:

```prisma
createdAt        DateTime  @default(now())
updatedAt        DateTime  @updatedAt
lastDiscoveredAt DateTime?
discoveredAt     DateTime
observedAt       DateTime?
```

### Decision

**Accepted timestamp semantics:**

| Field | Meaning | Update rule |
| --- | --- | --- |
| `Application.createdAt` | Time the internal application registry row was created | Set once by the database default; never changed by discovery |
| `Application.updatedAt` | Time the Application row was last changed through the persistence layer | Managed by Prisma `@updatedAt`; not a substitute for discovery time |
| `Application.lastDiscoveredAt` | Time the latest complete successful installed-application discovery updated the application | Update only after successful discovery; do not advance on failed or partial responses |
| `ApplicationDeployment.discoveredAt` | Time the current deployment snapshot was successfully captured and normalized | Set for the current successful snapshot |
| `RuntimeContainer.observedAt` | Time the runtime source reported the current container observation | Refresh when the current runtime row is updated or inserted |

All values represent instants. The persistence layer should use a consistent UTC/instant convention; the exact serialization convention is an implementation detail to settle before production migration.

### Consequences

- A stale `lastDiscoveredAt` indicates discovery freshness, not necessarily a stopped application.
- `updatedAt` may change for metadata edits even when no new discovery occurred.
- `discoveredAt` is deployment-state time; `observedAt` is runtime-state time.
- Historical time series are not implied by these fields because deployment and runtime history are deferred.
- The current schema expresses these field shapes, and the application layer must enforce the update semantics.

## ADR-010 Table Naming

### Context

The conceptual documentation uses PascalCase model names and snake_case examples, while the implementation instructions require PascalCase model names and camelCase fields. The current schema uses Prisma defaults and does not define `@@map`.

### Options

1. Use Prisma default model/table naming.
2. Use `@@map` and `@map` to force snake_case database names.
3. Use a separate project-wide naming convention later.

### Decision

**Accepted:** use default Prisma naming for v1. Keep PascalCase Prisma model names and camelCase Prisma field names. Do not add `@@map` or `@map` until a repository-wide database naming convention is explicitly adopted.

### Consequences

- The current schema remains consistent with the implementation instructions.
- Prisma model and field names are directly visible in the generated client.
- A later switch to snake_case would require explicit mappings and migration planning.
- This decision applies to the Application Registry only until a project-wide convention is accepted.

## ADR-011 Runtime Observation Retention

### Context

The source documents leave open whether `RuntimeContainer` stores only current state or historical observations. Historical records can support incident analysis, but they increase storage, reconciliation, and deletion complexity. The v1 Application Registry is an inventory foundation, not an operational event log.

### Decision

**Deferred:** historical runtime observation retention is deferred. For v1, use the current-only lifecycle in ADR-006 and replace/reconcile current rows after successful discovery. Do not add a history table, event table, validity interval, or snapshot version solely for runtime retention.

### Consequences

- The registry remains small and focused on current inventory.
- Previous container states and recreated container identities are not queryable after replacement.
- A future history requirement must define retention, ordering, source authority, and storage shape before adding a model.
- No new table is justified by the current milestone.

## Implemented Prisma Impact

The following decisions are encoded in the current `prisma/schema.prisma`:

1. All eight model IDs use `String @id @default(uuid())`.
2. `Application.name` is unique and `Application.zimaosAppId` is nullable unique; no redundant ordinary external-ID index is present.
3. `ApplicationDeployment.applicationId` is unique for the current deployment cardinality.
4. `ApplicationService` uses `@@unique([deploymentId, name])`.
5. `EnvironmentVariable` uses `@@unique([serviceId, key])`.
6. `RuntimeContainer.containerId` is unique for the current single-runtime-host assumption.
7. Child snapshot relations use `onDelete: Cascade`.
8. Foreign-key relations use `onUpdate: Restrict`.
9. The root `Application -> ApplicationDeployment` relation has no explicit `onDelete`; root deletion remains deferred.
10. `DeploymentPort.target` remains `Int` and no port-range fields are present.
11. Default Prisma naming is used without `@map` or `@@map`.

The following are application-layer semantics rather than additional Prisma structures:

- current-only runtime reconciliation after a complete successful discovery
- keeping internal IDs independent from external identities
- updating discovery timestamps only after successful discovery
- redacting Compose and environment values before persistence
- preserving the distinction between desired deployment state and actual runtime state

## Decisions Still Deferred

The following items remain intentionally deferred because they require broader product or operational policy rather than a safe local schema assumption:

- secret storage backend and whether any secret reference should ever be persisted
- deployment history beyond the current deployment snapshot
- historical runtime observation retention
- exact mapping of ZimaOS fields not represented by the eight models, including title locale selection, app type normalization, healthcheck, restart policy, command, env-file paths, and `x-casaos` metadata
- support for Compose target port ranges and advanced long-form port syntax
- multi-host runtime identity scoping if the control center later observes more than one Docker host
- application-level stale/deleted status policy when an application disappears from ZimaOS
